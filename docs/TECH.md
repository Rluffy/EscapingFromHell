# TECH – Escaping From Hell

Festgelegt mit dem Nutzer. Entscheidungen, die ein Agent selbst trifft, hier eintragen (Abschnitt „Entscheidungslog").

## Ziel-Hardware

- Echtes NES-Modul, **NTSC (60 Hz)**.
- **MMC3 (Mapper 4)** mit Batterie-RAM. Startwert: 128 KB PRG-ROM, 128 KB CHR-ROM, 8 KB PRG-RAM. Größen anpassen, wenn nötig (hier eintragen).
- Pro Boss und Phase eigene CHR-Bänke (Bank-Wechsel für Phasen und Overworld-Animation).

## Toolchain

- **cc65 2.19**: C für Logik, `ca65`-Assembler für Zeitkritisches (NMI, Scrolling, Sprite-DMA). Keine Fremd-Bibliothek (kein neslib): eigene Mini-Runtime in `src/crt0.s`, C-Laufzeit aus `none.lib`.
- Build: `make` baut `build/EscapingFromHell.nes`. `make clean`, `make test`.
- Python 3 mit Pillow für Skripte in `tools/`.
- Emulator/Tests: **Mesen2 2.1.1 Linux x64** in `tools/mesen/` (nicht im Git). Download: GitHub-Release `SourMesen/Mesen2`, Datei `Mesen_2.1.1_Linux_x64.zip`.
- Ausweichlösung, falls Mesen headless nicht läuft: `fceux` + `xvfb` (`xvfb-run`).
- Installationen (erlaubt): `apt install cc65 gh xvfb python3-pil`.

## Build-Layout

- `Makefile`: `src/*.c` → `cc65 -t none -O -Cl --cpu 6502` (`-Cl` = lokale Variablen statisch, siehe „Fehlersuche v1.0“) → `build/*.s` → `ca65`; `src/*.s` → `ca65`; Link mit `ld65 -C cfg/mmc3.cfg ... none.lib`. Ausgabe `build/EscapingFromHell.nes` (262160 Byte = 16 + 128 KB PRG + 128 KB CHR), dazu `.map` und `.lbl` in `build/`.
- `src/crt0.s`: iNES-Header (Mapper 4, Batterie, 8 PRG-Einheiten à 16 KB, 16 CHR-Einheiten à 8 KB, 1 PRG-RAM-Einheit à 8 KB, NTSC), Reset (PPU-Warmup, MMC3-Init, RAM löschen, C-Stack, `copydata`/`zerobss`, `main`), NMI (OAM-DMA von `$0200`, bei `col_pending` `ppu_flush`, dann `$2000` = `ppu_ctrl` und Scroll X = `scroll_x`, `frame_count` erhöhen), IRQ-Stub (`rti`), Vektoren, `wait_vblank()`.
- `src/ppu.s` (v1.0): schnelle `$2007`-Schreibroutinen für Bildaufbauten (`ppu_fill`, `ppu_copy`, `scene_draw`, `oam_hide`, `col_tiles`, `pair_meta`, `col_attr`), siehe „Bildaufbau (v1.0)“. Die Metakachel-Tabellen (`meta_tl/tr/bl/br/pal*`) und `cell_meta[]` liegen in `src/main.c` (fester Bereich, `#define META_DEF` vor `meta.h`), `menu.c` und `ppu.s` nutzen sie als `extern`.
- `src/ui.h` (generiert von `tools/art/uiart.py`: Kachel-IDs von Logo, Satzzeichen, Himmel, Sonne, Berge, siehe „Titel, Intro und Ende (v0.9)“), `src/meta.h` und `src/arena.h`: generierte Tabellen/Kachel-IDs der Hintergrund-Kunst (`tools/art/bgart.py`, siehe `Hintergrund-Kunst (v0.9)`). `src/debug.s`: Testvariablen (Segment `DEBUG`). `src/chr.s`: CHR-Daten, 16 `.incbin`-Blöcke an festen CHR-Offsets (Tabelle „CHR-Layout (v0.9)"). `src/map.s`: Overworld-Karte (`.incbin build/overworld.bin`, Symbol `_overworld_map`, Segment `BANK10`, nur lesbar solange die UI-Bank eingeblendet ist). `src/main.c`, `src/nes.h`: C-Seite (Zustandsmaschine, Overworld, PPU-Register-Makros, Prototypen). `src/dungeon.c`: Dungeon-Arena (siehe Abschnitt „Dungeon (v0.3)"). `src/menu.c`: Titel, Startmenü, Intro und Endbild (UI-Bank 10, siehe „Titel, Intro und Ende (v0.9)"). `src/boss.h`: Boss-Rahmen-Strukturen und Prototypen, geteilt zwischen `dungeon.c` (fest) und den Boss-Dateien (gebankt). `src/imp.c`: Imp (Code + Phasendaten in PRG-Bank 0). `src/ghost.c`: Geist (Bank 1). `src/hound.c`: Knochenhund (Bank 2). `src/snake.c`: Lavaschlange (Bank 3). `src/winged.c`: Geflügelter Dämon (Bank 4). `src/mirror.c`: Spiegeldämon (Bank 5). `src/toad.c`: Riesenkröte (Bank 6). `src/spider.c`: Spinnenkönigin (Bank 7). `src/oni.c`: Oni-Kriegsherr (Bank 8). `src/lord.c`: Höllenfürst (Bank 9).
- Makefile-Regeln: `assets/sprites/<n>.png` → `build/<n>.chr` (`png2chr.py --pad`: 2048 Byte für `tiles`, `anim_a`, `anim_b`, `common`, 4096 Byte für `boss01..boss10`; Tabelle `PAD_<n>` im Makefile); `assets/overworld.txt` → `build/overworld.bin` (`tools/mapconv.py`).
- CHR-Bänke: siehe „CHR-Layout (v0.9)". `crt0.s` setzt beim Reset R0..R5 = 0, 2, 6, 8, 9, 10 (Hintergrund, Animationsbild A, Sprite-Grundsatz, Boss 1); Hintergrund `$0000`, Sprites `$1000` (PPUCTRL `$88`).

### Linker-Konfiguration `cfg/mmc3.cfg`

- CPU-Speicher: `$0000-$00FF` Zeropage (cc65 + eigene), `$0100` Stack, `$0200-$02FF` OAM-Puffer, `$0300-$033F` `DEBUG` (Spielzustand, belegt bis `$033C`, `$033D-$033F` frei), `$0340-$05FF` BSS/DATA (704 Byte), `$0600-$07FF` C-Parameterstack (512 Byte, wächst abwärts von `$0800`), `$6000-$7FFF` Segment `SAVE` (Batterie-RAM; der Speicherstand belegt `$6000-$6006`, der C-Code greift direkt per Adresse zu, kein Linker-Symbol).
- PRG-ROM: MMC3 im PRG-Modus 0, Aufteilung siehe „PRG-Banking (v0.4)". Fest: `$C000-$FFFF` = Bänke 14/15 (`STARTUP`, `CODE`, `RODATA`, `DATA`-Ladebild, `VECTORS`). Umschaltbar: `$8000-$9FFF` (R6, Boss-Bank), `$A000-$BFFF` (R7, fest auf Bank 1, ungenutzt). Bänke 0..9 haben eigene Linker-Bereiche `BANK0..BANK9`, Bank 10 den Bereich `BANK10` (UI-Bank), Bänke 11..13 den Füllbereich `BANKS` (24 KB).
- CHR: ein Bereich `CHR` mit 128 KB, Segment `CHARS` (nur `src/chr.s`, Layout siehe „CHR-Layout (v0.9)").
- Reset-Init des MMC3: PRG-Modus 0, Bänke 0/1, vertikale Spiegelung (`$A000` = 0, `1` = horizontal), PRG-RAM an (`$A001` = `$80`), IRQ aus (`$E000`).

## Grafik-Pipeline

- Quelle: PNG in `assets/sprites/` (indiziert, NES-Palette, max. 4 Farben pro Palette).
- `tools/png2chr.py` wandelt PNG → CHR-Daten beim Build. Aufruf: `python3 tools/png2chr.py in.png out.chr [--pad N]` (Breite/Höhe Vielfaches von 8; `--pad 4096` füllt auf 4 KB Pattern-Table mit Nullen, Fehler wenn größer).
- Ausgabe: 2bpp-CHR, Kacheln zeilenweise (links→rechts, oben→unten), je 16 Byte: 8 Byte Plane 0 (niedriges Bit), 8 Byte Plane 1 (hohes Bit), MSB = linkes Pixel.
- Farbzuordnung: Palette-PNG → Pixelindex 0..3 direkt. RGB/RGBA-PNG → transparent oder #000000 = 0, übrige Farben nach Helligkeit aufsteigend = 1, 2, 3. Mehr als 4 Farben im Bild = Fehler.
- `assets/sprites/tiles.png` (seit v0.9 Paket 2: **128×64 px = 128 Kacheln, 16 pro Zeile**, Kachel-ID = Zeile×16 + Spalte; vorher ein Streifen 400×8) ist der Hintergrund-Pattern-Table R0. Belegung (X, Z und die Satzzeichen . ! ? stehen seit v0.9 Paket 5 als Kacheln 152..156 in R1, nicht hier, R0 ist voll): 0 leer (Leerzeichen, Text), 13..39 Schrift 5x7 in den Spalten 1–5 Farbe 3 (13 I, 14 M, 15 P, 16–25 Ziffern 0–9, 26 D, 27 U, 28 N, 29 G, 30 E, 31 O, 32 V, 33 C, 34 T, 35 R, 36 Y, 37 A, 38 S, 39 H), 40 HP-Balken voll (Zeilen 1–6 Index 3), 41 halb (linke 4 Spalten Index 3, rechte Index 2), 42 leer (Index 2), 43 B, 44 L, 45 J, 46 K, 47 W, 48 F, 49 Q; **Arena-Kacheln** (feste IDs, die Tests/Code kennen): 3 Lavabecken-Oberfläche, 10 Ziegel (Wand/Boden-Füllung/Decke), 11 Boden-Oberkante, 12 Plattform Mitte; weitere Arena-Kacheln (Plattform-Enden, Balken, Säulen, Wandfeld, tiefe Lava) und die **Overworld-Kacheln** (Metakacheln, siehe `Hintergrund-Kunst (v0.9)`) füllen die freien IDs 1, 2, 4..9 und 50..127 sowie Kachel-IDs ab 128 (R1). Tor-Kacheln: oben links des verschlossenen Tors = **7**, des offenen Tors = **8** (die Tests lesen diese IDs im Nametable). Neue Buchstaben für weitere Namen/Texte: Kacheln anhängen (Sheet wachsen lassen) und die Kachelnummer in `ftile[]` (`dungeon.c`, Index = Buchstabe − 'A', 0 = fehlt, zeigt leer) eintragen. Für GHOST waren keine neuen Buchstaben nötig (G H O S T gibt es schon). Für BONE HOUND und GOT DOUBLE JUMP kamen B (43), L (44), J (45) dazu (Blatt 368×8, 46 Kacheln, 736 Byte). Für LAVA SNAKE kam K (46) dazu (Blatt 376×8, 47 Kacheln, 752 Byte). Für WINGED DEMON und GOT FIREBALL kamen W (47) und F (48) dazu (Blatt 392×8, 49 Kacheln, 784 Byte; `ftile[22]` und `ftile[5]`). Für das Startmenü und das Endbild (v0.8: ESCAPING FROM HELL, NORMAL, CHEAT, YOU ESCAPED, PRESS START) waren **keine neuen Buchstaben** nötig, `tiles.png` blieb unverändert. Für SPIDER QUEEN kam Q (49) dazu (Blatt 400×8, 50 Kacheln, 800 Byte; `ftile[16]`; die übrigen Buchstaben S P I D E R U N gab es schon).
- Sprite-Blätter (seit v0.9, vorher ein Blatt `player.png` mit 256 Kacheln): `common.png` (Spieler, Schwert, Herzen, gemeinsame Projektile), `boss01.png` .. `boss10.png` (je ein Boss) und `anim_a.png`/`anim_b.png` (Overworld-Animation, Hintergrund-Seite). Alle 16 px breit, wachsen nach unten (je 16×16-Block = 4 Kacheln zeilenweise), Kachelnummer = Zeile×2 + Spalte. Kachelinhalte und Layout: „CHR-Layout (v0.9)". Die Kachelnummern in den Boss-Abschnitten unten (z. B. Geist `tile` 32 / 38 / 44) sind die **alten** absoluten Nummern vor v0.9; heute gilt `BT + (Nummer − erste Kachel des Bosses)`, z. B. Geist `BT + 0 / 6 / 12`.
- Nutzer kann jede PNG ersetzen. Hintergrund-Art-Pass (v0.9 Paket 2): `tools/art/bgart.py`, siehe `Hintergrund-Kunst (v0.9)`. Sprite-Art-Pass (v0.9 Paket 3a, Held, gemeinsame Sprites, Dämonen 1–5): `tools/art/sprart.py`, siehe `Sprite-Kunst (v0.9)`; Dämonen 6–10 (Paket 3b, `boss06.png` .. `boss10.png`) ebenfalls aus `sprart.py`.
- NES-Grenzen beachten: 64 Sprites, max. 8 pro Zeile. Große Dämonen = Sprites + Hintergrund-Kacheln.

- **Wechsel:** `bank_set(b)` (`crt0.s`, `__fastcall__`, Bank in A) schreibt R6 und merkt sich `b` in `cur_bank` (Debug `$0326`; Reset setzt 13 = keine; Imp-Dungeon: 0). Nur aus der Hauptschleife aufrufen. `dungeon_enter()` ruft `bank_set(bs->bank)`, die Bank bleibt für den ganzen Kampf eingeblendet; `leave_dungeon()` und `main()` (Boot) blenden die UI-Bank (`BANK_UI` = 10, `nes.h`) wieder ein, `end_enter()` wird nach `bank_set(BANK_UI)` gerufen. Es gibt keinen Wechsel pro Frame. **Regel (v0.9):** Der Code der UI-Bank (`menu.c`) und die Karte sind nur lesbar, solange Bank 10 eingeblendet ist (alle Zustände außer dem Dungeon); fester Code, der die Karte oder `menu.c` nutzt, darf nie im Dungeon-Zustand laufen. Eine gebankte Funktion darf `bank_set` nie selbst rufen (die Rückkehr läge in der falschen Bank); Wechsel passieren nur in festem Code (`main.c`, `dungeon.c`).
- **NMI:** ruft nie gebankten Code und fasst `$8000/$8001` nicht an (nur `ppu_flush` im festen Bereich). Wird später per NMI umgeschaltet (z. B. CHR-Bänke), muss der NMI das Select-Register `$8000` danach wieder auf den Wert der Hauptschleife setzen (Race) und `cur_bank` bleibt unberührt, weil nur R6 PRG ist.
- **Regeln für gebankten Code (cc65):** Gebankte Funktionen rufen nur Festbank-Code (Kern, cc65-Laufzeit in `CODE`) oder Code derselben Bank, nie eine andere Bank. Daten, die NMI-Zeit oder andere Bänke lesen, nicht in eine Bank legen. Boss-Tabelle (`bosses[]` in `dungeon.c`), Namen und Max-HP bleiben fest (die Bank-Nummer muss lesbar sein, bevor die Bank da ist). Zustand (Boss-RAM, `fb_*`, `rng`, ...) liegt wie bisher im RAM (`dungeon.c`, `extern` in `boss.h`).
- **Neuer Boss in einer Bank:**
  1. `src/<boss>.c` anlegen mit `#pragma code-name("BANKn")` und `#pragma rodata-name("BANKn")` ganz oben (n = freie Bank 0..9; mehrere kleine Bosse dürfen sich eine Bank teilen), `#include "nes.h"` und `"boss.h"`. Funktion `void <boss>_ai(void)` und `const struct phase <boss>_ph[3]`. Vorlage: `src/imp.c`.
  2. `boss.h`: Prototyp und `extern` ergänzen. `dungeon.c`: Eintrag in `bosses[]` (`{ name, hp, n, w, h, y0, <boss>_ai, <boss>_ph }`), `NBOSS` erhöhen. Bänke 0..9 haben ihre Linker-Bereiche schon; für Bank n > 9 zuerst im Linker-Config einen Bereich/ein Segment aus `BANKS` abspalten (Muster `BANK9`, `BANKS` schrumpft um 8 KB).
  3. Neue Quelldatei wird vom Makefile automatisch gebaut (`src/*.c`). `make` und `build/EscapingFromHell.map` prüfen: Segment `BANKn` ≤ `$2000` Byte, nichts davon in `CODE`/`RODATA`.
  4. Kacheln: eigenes Blatt `assets/sprites/boss<NN>.png` (NN = Dungeon-Nr.) und Phasen-`tile` = `BT + n` (siehe „CHR-Layout (v0.9)"); Palette wie bisher (Tabelle `struct phase`), Test wie `tests/boss.lua` (`cur_bank` = n prüfen); `src/chr.s` hat die zehn Boss-Blöcke schon.

## CHR-Layout (v0.9)

MMC3-CHR-Modus: Bit 7 von `$8000` = 0 (**keine** A12-Invertierung). R0/R1 = 2-KB-Bänke bei `$0000`/`$0800` (Hintergrund-Pattern-Table, PPUCTRL Bit 4 = 0), R2..R5 = 1-KB-Bänke bei `$1000/$1400/$1800/$1C00` (Sprite-Pattern-Table, PPUCTRL Bit 3 = 1). `chr_set(r, bank)` (`crt0.s`, `__fastcall__`) schreibt `$8000` = r und `$8001` = Bank; nur aus der Hauptschleife (der NMI fasst `$8000` nicht an), bei ausgeschaltetem Bild oder direkt nach `wait_vblank()`. Bankzahlen in 1-KB-Einheiten (R0/R1 ignorieren Bit 0). `png2chr` füllt jedes Blatt mit Nullen auf seinen Platz auf, `src/chr.s` legt die Blöcke der Reihe nach ab (Offsets fest). CHR-ROM 128 KB, belegt 48 KB (Bank 0..47), Rest frei.

| 1-KB-Bank | Register | PPU-Adresse | Kachel-IDs | Inhalt (Quelle) |
|---|---|---|---|---|
| 0-1 | R0 = 0 | `$0000-$07FF` | 0..127 | Hintergrund fest: Schrift 13..39 und 43..49, HP-Balken 40..42, Arena-Kacheln (3, 10..12 und weitere aus 1, 2, 4..9, 50..55), Overworld-Kacheln (freie IDs bis 127) (`tiles.png`, 16 Kacheln pro Zeile) |
| 2-3 | R1 = 2 | `$0800-$0FFF` | 128..255 | Overworld-Animation, Bild A (`anim_a.png`, 128×64 px, ID = 128 + Zeile×16 + Spalte): Lava, Laternen, Gras, Augen (animiert) plus der Rest der Overworld-Kacheln (statisch, in A und B gleich); in Menü, Arena und Endbild bleibt, was zuletzt eingestellt war (dort unbenutzt) |
| 4-5 | R1 = 4 | `$0800-$0FFF` | 128..255 | Overworld-Animation, Bild B (`anim_b.png`, dieselben IDs; nur die animierten Kacheln unterscheiden sich) |
| 6-7 | R2 = 6 | `$1000-$13FF` | 0..63 | Sprites fest (`common.png`, Details „Sprite-Kunst (v0.9)“): 0..3 Overworld-Spieler stehend, 4..7 Dungeon-Spieler stehend, 8..11 Gehen A, 12/13 Schwert, 14/15 Herz voll/leer, 16 Schwertwelle (`WAVE_TILE`), 17 Schockwelle (`SHOCK`, boss.h; Oni und Höllenfürst), 18..21 Gehen B, 22..25 Sprung, 28 Boss-Feuerball, 29 Spieler-Feuerball, 30/31 Schild, 32..35 Overworld-Spieler Gehen; 26/27 und 36..63 frei; Bank 7 ungenutzt |

- **Boss-Blätter:** `dungeon_enter()` setzt (bei ausgeschaltetem Bild) `boss_chr` = `CHR_BOSS(cur_dungeon)` = `8 + 4 * (n − 1)` und `chr_set(3..5, boss_chr + 0..2)`. Pro Boss stehen 4 KB zur Verfügung, davon sind R3..R5 = 3 KB (192 Kacheln) sichtbar; die 4. KB ist Reserve. Kachel 0 des Blatts hat die ID `BT` = `0x40` (boss.h): Bosscode nutzt `BT + n` (Zeile×2 + Spalte im PNG), nie absolute Zahlen. Alle heutigen Bosse passen in 1 KB (R3, IDs `0x40..0x7F`); größere Blätter (mehr als 64 Kacheln, PNG länger als 256 px) laufen automatisch in R4/R5 (IDs `0x80..0xFF`). Gemeinsame Kacheln gehören in `common.png` (IDs < 0x40), nicht in jedes Boss-Blatt.
- **Neue Grafik für einen Boss (Art-Pass):** `assets/sprites/boss<NN>.png` überschreiben (16 px breit, Reihenfolge der Kacheln ändern nur zusammen mit `struct phase.tile` und den Offsets im Boss-Code; heutige Belegung: Imp 0..11, Geist/Hund/Schlange/Geflügelter je 0..17, Spiegel 0..23 mit Kopien-Köpfen 18..23, Kröte 0..39 mit Zunge 36/37, offenem Maul 38, Schleim 39, Spinne 0..20 mit Faden 18, Netz 19 (`WEB_TILE`), Spinnling 20, Oni 0..29 mit Keule 30/31, Höllenfürst 0..17). `make` baut es neu (Fehler, wenn über 4 KB). - **UI-Kacheln (v0.9 Paket 5):** die statischen IDs **152..240** von R1 (in Bild A und B gleich, kein Flackern) gehören `tools/art/uiart.py`, siehe „Titel, Intro und Ende (v0.9)“; frei bleiben 241..255.
- **Overworld-Animationshaken:** `anim_tick()` (`main.c`) läuft in jedem Zustand außer Dungeon (Overworld, Titel, Intro; im Endbild harmlos), direkt nach `wait_vblank()` (die Umschaltung muss im VBlank passieren). Bild A und Bild B sind zwei PNGs mit denselben Kacheln, nur die animierten unterscheiden sich. Die Takt-Konstante steht in `main.c`. - **Test:** `tests/chr.lua` (siehe „Tests"): vergleicht die PPU-Sicht auf `$0000/$0800/$0FF0/$1000/$1400/$1800/$1C00` (`emu.memType.nesPpuMemory`) mit dem CHR-ROM (`emu.memType.nesChrRom`) an der erwarteten Bank. ## Soundeffekte (v0.9)

- **Code:** `src/sfx.s` (fester Bereich, `CODE`; Aufrufer in Boss-Bänken dürfen `sfx_play` rufen). `$4015` = `$0B` (Pulse 1, Pulse 2, Rauschen an) setzt `crt0.s` im Reset, `$4017` = `$40` stand dort schon. `sfx_play(id)` (`__fastcall__`, A = Id 1..18, keine Bereichsprüfung) startet einen Effekt, `sfx_update()` läuft **einmal pro Frame am Ende der Hauptschleife** (nach der Zustandsverarbeitung, nicht im NMI und nicht direkt nach `wait_vblank`: direkt nach dem Vblank-Start braucht der PPU-Zugriff (Paletten, Text) jeden Zyklus; ein erster Versuch dort ließ `tests/boss.lua` an der Phasenpalette scheitern).
- **Kanäle:** 0 = Pulse 1 (Spieler), 1 = Pulse 2 (Boss, Jingles), 2 = Rauschen (Treffer, Schläge, Dumpfes). Pro Kanal läuft ein Effekt. Priorität je Effekt: ein neuer Effekt ersetzt den laufenden auf demselben Kanal, wenn seine Priorität **>=** der des laufenden ist, sonst wird er verworfen (Kanal frei = Priorität 0).
- **Daten:** Ein Effekt ist eine Folge von Schritten zu je 5 Byte: Dauer in Frames, dann die vier APU-Register des Kanals (Pulse: Duty/Lautstärke, Sweep, Periode lo, Periode hi; Rauschen: Lautstärke, -, Modus/Periode, -); Dauer 0 beendet den Effekt (Lautstärke 0 wird geschrieben). Konstante Lautstärke und gehaltener Längenzähler (Bit 4/5), die Lautstärke steht je Schritt in den Daten. Die Hardware-Sweep-Einheit macht die Tonhöhen-Rutsche von Sprung und Doppelsprung; alle anderen Effekte ändern die Periode schrittweise. Tabellen `fx_cp` (Kanal + 4 × Priorität), `fx_lo`/`fx_hi` (Zeiger) in Id-Reihenfolge; Ids als `SFX_*` in `src/nes.h`. **Lautstärke:** höchstens 10 von 15 (Pulse meist 3..9, Rauschen bis 10), kein langer Effekt über 8; `tests/sfx.lua` prüft das.
- **Periodenregel:** Pulse-Perioden bleiben <= 1023 (der Sweep-Zieltest schaltet den Kanal bei größerem Ziel stumm, auch bei ausgeschaltetem Sweep).
- **Effekte:**

## Overworld (v0.2)

- **Karte:** `assets/overworld.txt` (Text, 64 Spalten x 15 Zeilen Metakacheln à 16x16 px = 1024x240 px, Legende im Dateikopf). `tools/mapconv.py` macht daraus `build/overworld.bin`: spaltenweise, 16 Byte pro Spalte (Zeile 15 = Füllbyte 0), 1024 Byte. Zell-ID = Index in der Metakachel-Tabelle (`src/meta.h`, siehe `Hintergrund-Kunst (v0.9)`): 0 Boden (10/11 Varianten), 1 Pfad (12 Variante), 2 Fels/Berg (13/14 Varianten), 3 Lava (15/43 Varianten), 4 Mauer, 5 Dach Mitte (6/7 Dachenden links/rechts), 8/9 Tempelwand links/rechts der Tür, 16..25 = Tor von Dungeon 1..10, 32..41 = Tür von Dungeon 1..10, 26 toter Baum, 27 Laterne, 28 Gras, 29 Totenkopf, 30 Knochen, 31 Augen (Kartenzeichen `o`). Jede Metakachel besteht aus **4 verschiedenen 8x8-Kacheln** (oben links, oben rechts, unten links, unten rechts) und hat eine Palette (Attribut-Granularität 16x16). Kartenzeichen und Regeln: Varianten von `, . # ~` wählt `mapconv.py` per Positions-Hash, `W` und `R` per Nachbarn (Mauer neben einer Tür wird Tempelwand, Dach-Lauf bekommt Enden); neue Dekorzeichen `T` Baum, `L` Laterne, `y` Gras, `k` Totenkopf, `x` Knochen, `o` Augen. Kollision (`solid()` in `main.c`): fest sind Fels, Lava, Mauer, Dach, Tempelwand, Baum, Laterne und verschlossene Tore; frei sind Boden, Pfad, Tür, offenes Tor, Gras, Totenkopf, Knochen, Augen (Dekor ändert keinen Weg: Zeilen 9 und 10 am Start bleiben frei). Der Metakachel-Aufbau im Code: `cell_meta[]` bildet Tore (16..25) auf 16/42 (verschlossen/offen, je nach `is_open`) und Türen auf 32 ab, `build_col()` schlägt pro Zelle `meta_tl/tr/bl/br/pal` nach und cacht die Metakachel-Indizes je Attributpaar (`pair_c`, wird bei jedem Neuaufbau und jeder Tormaske neu gesetzt).
- **Tempelraster:** Tür von Dungeon n in Spalte 6n-3, Zeile 5 (n ungerade) bzw. 3 (n gerade); Dach darüber, Tor direkt darunter, dann ein Pfadstück zum Hauptweg. Start des Spielers: x=32, y=144. Der Code (Rückkehr aus dem Dungeon) und `mapconv.py` (Assert) nutzen dieselbe Formel.
- **Tore:** offen, wenn n == 1 oder Bit n-2 in `dungeons_cleared` gesetzt ist. Zeichnen und Kollision fragen dieselbe Funktion (`is_open`). Das Tor ist als Zell-ID in der Karte, die Metakachel (16 verschlossen = orange Siegel-Tor, 42 offen = blauer Bogen; oben links Kachel 7 bzw. 8) wird beim Spaltenaufbau gewählt. Ändert sich die Maske, zeichnet das Spiel alle sichtbaren Spalten neu (Bild kurz aus), ebenso beim Betreten der Overworld.
- **Scrolling:** vertikale Spiegelung (zwei Nametables nebeneinander = 512 px Ring), `PPUCTRL`-Bit 0 + `PPUSCROLL` X aus `cam_x` (Kamera zentriert auf den Spieler, 0..768). Wechselt `cam_x >> 4`, baut die Hauptschleife die nächste Metakachel-Spalte (rechts: `spalte+16`, links: `spalte`) in `colbuf` (2 Kachelspalten à 30) und `attrbuf` (8 Attribut-Bytes) und setzt `col_pending`. Der NMI kopiert nach dem OAM-DMA beides (Inkrement 32, ca. 1300 Zyklen, passt in VBlank). Attribut-Byte deckt zwei Metakachel-Spalten, wird deshalb immer aus beiden Spalten berechnet. Weiter als eine Spalte Sprung (Teleport) oder Maskenänderung: kompletter Neuaufbau bei ausgeschaltetem Bild (`redraw_overworld`).
- **Spieler:** 16x16 Metasprite (4 Sprites, Kacheln 0..3, Palette 0), 2 px/Frame, 8 Richtungen. Kollisionsbox: 8x6 px an den Füßen (x+4..x+11, y+10..y+15) gegen die Zellen. Eintritt: Fußmitte (x+8, y+12) auf Tür-Zelle eines offenen Dungeons + **A**.
- **Dungeon:** `game_state` 3, Details im nächsten Abschnitt. Rückkehr (Sieg oder Start+Select) setzt den Spieler auf die Tür-Zelle.
- Eingabe: Controller 1, `read_pad()` in `main.c`.
- Paletten (seit v0.9 Paket 2, `pal_overworld` in `main.c`, Hintergrund immer `$0F` schwarz): 0 Boden/Pfad/Fels/Baum/Knochen blau-violett-lavendel `02 03 32`, 1 Wände/Säulen/Türen rot `06 16 26`, 2 Lava/Laternen/verschlossenes Siegel rot-orange-gelb `16 27 38`, 3 Dächer/offenes Tor violett-blau-cyan `03 12 21`; Sprite-Palette 0 braun/blau/Haut.

## Boss-Rahmen (v0.3)

- **Tabelle** `bosses[]` in `dungeon.c` (Index = Dungeon-Nr. − 1; 10 Einträge, jeder Dungeon hat einen Boss). Eintrag `struct boss`: `name` (Großbuchstaben aus `font[]`), `hp` (Max-HP), `bank`, `w`/`h`/`y0` (Sprite-Breite 16, 24 oder 32 px, Sprite-Höhe 16, 24 oder 32 px, Start-y; ab `w` >= 32 oder `h` >= 32 (`OWN_DRAW` in `dungeon.c`) zeichnet `draw()` den Boss nicht, die KI schreibt ihre Sprites selbst (Riesenkröte, Oni-Kriegsherr, Höllenfürst); `arena_reset` setzt `en.w`/`en.h`/`en.y` daraus), `ai` (Funktionszeiger, läuft jeden Frame), `ph[3]` je Phase `struct phase`: `tile` (erste von 4 Sprite-Kacheln), `spd`/`wait` (Hüpfen), `rate`/`shots`/`fspd` (Feuerbälle), `pal[3]` (Sprite-Palette 1). Neuer Dämon = Tabelleneintrag + `*_ai()` + Phasendaten in einer Bank (Schritte: „PRG-Banking (v0.4)") + Kacheln, `NBOSS` erhöhen. `bosses[]` hat jetzt `bank` und `ph` (Zeiger auf die Phasen in der Bank) statt eingebetteter Phasen.
- **Phasen:** beim Reset aus Max-HP berechnet: Phase 2 ab `hp <= max*70/100`, Phase 3 ab `hp <= max*50/100` (Imp, Max-HP 10: 7 und 5; genau 70 % bzw. 50 % zählt schon zur nächsten Phase). Geprüft nach jedem Schwerttreffer.
- **Phasenwechsel-Effekt:** `boss_fx` = 30 Frames: Boss eingefroren, harmlos und nicht treffbar, alle Feuerbälle weg, Hintergrundfarbe blinkt weiß (4 Frames an/aus), neue Kacheln und Palette gelten sofort. Palette und Namenstext werden am Frame-Anfang (`pal_sync()`, `text()`) direkt in den PPU geschrieben, solange noch VBlank ist (danach `PPU_ADDR` = 0, Arena scrollt nie); deshalb muss diese Arbeit kurz bleiben (Textlöschen ohne Buchstabensuche).
- **Intro:** `dungeon_enter` zeichnet den Namen zentriert in Kachelzeile 10 (Bild aus), `intro` = 75 Frames (1,25 s): Spieler, Boss, Feuerbälle stehen, nur Zeichnen läuft. Danach Text löschen, Kampf. Nach dem Neustart bei 0 Herzen kein Intro.
- **Gegner-HP-Balken** (`bar_sync()` in `dungeon.c`, generisch): 10 Hintergrundkacheln in Nametable-Zeile 2, Spalten 20..29 (`$2054..$205D`), Kacheln 40 voll / 41 halb / 42 leer. Halbschritte = `ceil(hp * 20 / hp_max)` (`hp_max` = Boss-Tabelle), Kachel i voll ab Schritt 2i+2, halb bei 2i+1. Neuzeichnen nur, wenn `en.hp` != `bar_hp` (zuletzt gezeichnet, 255 = erzwingen). Beim Betreten bei ausgeschaltetem Bild gezeichnet (also schon im Intro), danach über denselben Puffer wie Texte (`tb[]`, 12 Byte): `bar_sync()` am Anfang von `draw()` füllt ihn, `text_flush()` schreibt ihn am nächsten Frame-Anfang im VBlank. Ist `tb[]` belegt (Text) oder steht ein Paletten-Update an (`pal_ph != boss_phase`), wartet der Balken einen Frame: Balken und Phasenpalette zusammen in einem VBlank passten nicht (die Palette kam nicht an, im Test aufgefallen). Dank Vergleich mit `en.hp` zeichnet sich der Balken auch nach `emu.write` auf HP und nach dem Neustart bei 0 Herzen neu. Herzen sind Sprites in derselben Zeile, der Balken liegt rechts davon (Hintergrund, zählt nicht zu den 8 Sprites pro Zeile).
- **Besiegt:** `en.hp` 0 → `boss_dead` = 1, Boss und Feuerbälle verschwinden, Arena bleibt, danach läuft der Sieg-Bildschirm (nächster Abschnitt).
- **Imp-KI (`imp_ai`, `src/imp.c`, Bank 0):** nur Boden. Steht `wait` Frames, hüpft dann (`vy` −4, Schwerkraft wie beim Spieler, ca. 30 px hoch, 24 Frames Flug) mit `spd` px/Frame in Richtung Spieler, in 1 von 4 Hüpfern weg. Unabhängig davon alle `rate` Frames `shots` Feuerbälle Richtung Spieler (Start nach 70 Frames). Phase 1 / 2 / 3: Hüpfpause 120 / 80 / 56, Tempo 1 / 1 / 2, Feuerball alle 300 / 200 / 240 Frames (`rate` ist deshalb 16 Bit, ebenso `fb_t`), Feuerball-Tempo überall 1, Phase 3 = Dreifach-Fächer (vertikal −1/0/+1 mit halber Rate, also flach: der untere Schuss trifft nach ca. 8 Frames den Boden, der mittlere läuft am Boden entlang und ist überspringbar, der obere steigt 0,5 px/Frame und fliegt ab ca. 20 px Abstand über den stehenden Spieler; ein Zweifach-Fächer war nicht nötig). Einzelschuss zielt nur nach oben (−1), wenn der Spieler höher steht.
- **Feuerbälle:** 3 Slots (`fb_x`/`fb_y` Debug, `fb_vx`/`fb_vy` intern), 8x8-Sprite (Kachel 28, Palette 2, OAM 52..63), verschwinden an Wänden, Boden und Oberkante. Treffer = −1 Herz (gleiche Routine `hurt()` wie Kontakt: Unverwundbarkeit und Rückstoß). Ein Spucken ohne freien Slot lässt Schüsse aus.
- **Hohe Bosse und `boss_hide`:** Ist `en.h` > 16, zeichnet `draw()` eine dritte Sprite-Reihe (OAM `$40..$47`, Kacheln `tile`+4/+5, Palette 1, `O_ENEMY2`). `boss_hide` (Debug `$0327`, vom Boss-KI-Code jeden Frame gesetzt, `arena_reset` löscht es): Bit 0 → `combat()` ignoriert Schwerttreffer und Kontakt, Bit 1 → keine Boss-Sprites. Für spätere unsichtbare/teleportierende Bosse wiederverwendbar. **Breite Bosse (24 px, Knochenhund):** `en.w` = 24 (aus der Boss-Tabelle); `draw()` nutzt dieselben zwei Sprites (OAM `$40`, `$44`) wie die dritte Reihe für die dritte Spalte (x+16, Kacheln `tile`+4/+5, obere und untere 8x8). Kontakt, Schwerttreffer und die Rückstoß-Klemmung rechnen mit `en.w`.
- **Kontakt/Schwert:** Imp 16x16, Kontakt kostet 1 Herz (nicht während `en.flash`), 10 HP, 1 Schaden pro Schlag, 12 Frames Trefferschutz (blinkt), Rückstoß `BOSS_KNOCK` = 16 px weg vom Spieler (sofort, Klemmung an den Wänden; nur Boss, der Test-Dummy bleibt). Sprites pro Zeile: Spieler 2 + Schwert 2 + Imp 2 + Feuerbälle (selten alle auf einer Zeile) = meist ≤ 8.

## Boss-Zufall und Kampfuhr (v1.0)

- **Kampfuhr `ftick`** (`unsigned char`, seit v1.0 Paket 2 Debug-Byte `$0342` in `debug.s`, `extern` in `boss.h`): zählt die Frames des laufenden Kampfes. `dungeon_frame()` erhöht sie am Anfang jedes Frames **außer im Intro und in der Pause**, `arena_reset()` setzt sie auf 0. Der Kampf beginnt also im Intro-Ende und nach einem Neustart bei 0 Herzen mit demselben Wert. **Alle** Bosse und der Rahmen nehmen `ftick` für Zeitabhängiges (Flackern per `boss_hide`, Geist-Schweben, Schlangen-Wackeln, Flügeldämon-Streifzug, Krötenschleim-Schwerkraft, Schuss-Halbtakt `fireballs()`, Helden-Gehbild in `draw()`), **nie** `frame_count`. `frame_count` bleibt NMI-Zähler (Overworld-Gehbild, Tests).
- **Zufall `rng`:** `arena_reset()` setzt `rng = cur_dungeon * 53 + 7` (fester Startwert je Dungeon); das passiert beim Betreten **und** beim Neustart bei 0 Herzen (beide rufen `arena_reset()`). Fortschreibung in den Boss-Dateien nur noch `rng = rng * 5 + 17;` (der alte Zusatz `+ frame_count` entfiel). Folge: Ein Kampf mit gleichen Eingaben ist Frame für Frame gleich, unabhängig von Spielgeschichte, Menüdauer und Codegröße.
- **Weitere Zustände, die den Verlauf beeinflussten:** Die Schlange setzte `side` (Becken links/rechts) nie zurück (alter Wert aus dem vorigen Kampf, jetzt `side = 0` in INIT). Bei den „eigenen Zeichnern“ (Kröte, Oni, Höllenfürst) lief die KI im letzten Intro-Frame schon mit `intro == 0` (Kampfstart einen Frame früher als nach einem Neustart): `bs->ai()` läuft jetzt **vor** dem Herunterzählen. Höllenfürst: `boss_hide` wird beim Wechsel FTELE/APPEAR → IDLE auf 0 gesetzt (der erste Frame des Schlagfensters trug sonst noch das Flackern des Vorzustands und war unsichtbar).
- **Test `tests/determinism.lua`:** für alle 10 Dungeons je 240 Spiel-Frames mit stehendem Spieler (keine Eingabe): (1) erster Eintritt, (2) nach Verlassen und erneutem Betreten mit anderem `frame_count`, (3) nach dem Neustart bei 0 Herzen müssen Boss (x, y, HP, Zustand, `boss_hide`, Phase), Herzen, Unverwundbarkeit, Schüsse und alle sichtbaren Sprites **identisch** sein. Abgetastet wird einmal pro Spiel-Frame beim Aufruf von `wait_vblank()` (Lua sucht die Adresse über das Byte-Muster der Funktion im festen Bereich, Exec-Callback): ein Frame, der den VBlank überschreitet, würde beim Abtasten am Frame-Ende halb fertig gesehen. **Befund (nicht behoben):** Die Lavaschlange überschreitet den VBlank in ca. einem Viertel ihrer Frames (79 von 300; ihr Körper in `body()` rechnet pro Segment zwei 16-Bit-Multiplikationen), der Kampf läuft dort also zeitweise mit 45 statt 60 Bildern pro Sekunde; Paket 2 (Fehlersuche) soll sie optimieren (Tabelle statt Multiplikation).
- **Straffere Tests** (vorher wegen Frame-Timing/Zufall gelockert, jetzt wieder eng): `smoke.lua` `frame_count` 146..156 nach 160 Frames (vorher ≥ 90), `toad.lua` Schleim landet bei x 52 ± 14 (vorher ± 24) und startet bei y 156 (vorher 150..160), `oni.lua` Phase-1-Schockwelle nur −2 (vorher ±2), erster Angriff muss die Keule sein (vorher durfte er fehlen), Phase 2 ohne provozierten Ersatz-Schlag, Phase-3-Steh-Bot ≤ 3 Herzen (vorher ≤ 4), Köder wartet wieder einfach 125 Frames, Sprungsuche 6 x 700 statt 10 x 900, `lord.lua` erstes volles Ruhefenster ohne Auswahl (`full(s, IDLE)`), `spider.lua` Spinnling bei y 176 (die Parität des Halbtakts entscheidet nicht mehr zufällig; `FLOOR_Y + 4` hing von der Parität ab, daher bleibt 176 als paritätsfeste Wahl). Unverändert gelockert bleiben die Steh-Bot-Grenzen des Höllenfürsten (≤ 4 je Phase, 3 / 3 / 4 gemessen): sie gehören zu Paket 3 (Balance).

## Bildaufbau (v1.0)

Vollständige Neuzeichnungen (Titel/Menü, Intro-Seiten, Endbild, Overworld, Arena) laufen bei ausgeschaltetem Bild und stehendem NMI; jeder Frame davon ist ein schwarzer Frame. Vorher brauchten die C-Schleifen mit `PPU_DATA`-Schreibzugriffen 7 bis 13 Frames, jetzt höchstens 3 (Messung `tests/redraw.lua`, zählt die Frames mit ausgeschaltetem Hintergrund in 40 Frames nach dem Auslöser):

| Neuzeichnung | vorher (Frames) | jetzt (Frames) |
|---|---|---|
| Menü: Frage DELETE SAVE / zurück | 12 / 12 | 2 / 2 |
| Intro starten / Seite blättern | 7 / 7 | 2 / 2 |
| Overworld (aus dem Intro) / Teleport | 12 / 12 | 3 / 3 |
| Dungeon 1 / 4 / 8 betreten | 10 / 11 / 10 | 2 / 3 / 3 |
| Dungeon verlassen (Overworld) | 12..13 | 3 |
| Endbild | 7 | 2 |

Die reine Arbeit liegt bei 1,7 Frames (Menü) bis 2,2 Frames (Overworld); der schwarze Bereich endet erst im nächsten VBlank (`screen_on` wartet darauf), deshalb 2 oder 3 Frames, Abstand zur 3-Frame-Grenze ca. 0,8 Frames.

- **`src/ppu.s`** (fester Bereich, ruft nie gebankten Code; Argumente `__fastcall__`): `ppu_fill(v, n)` schreibt `n` gleiche Bytes (Nametable leeren, 1024 Byte in ca. 9000 Zyklen), `ppu_copy(src, n)` kopiert 1..255 Byte (Palette 32, Attribute 64, Logo-Zeilen, Zeilenpuffer der Arena), `scene_draw(t, r0, n)` zeichnet `n` Metakachel-Zeilen einer Szenentabelle (`menu.c`, 16 Zellen je Zeile; die zwei Kachelzeilen einer Zellzeile sind 64 aufeinanderfolgende Nametable-Bytes, eine PPU-Adresse genügt) und ODERt die Palettenbits aller Zellen in `attr[]` (vorgeschobene Tabellen `meta_pal/2/4/6`), `oam_hide()` versteckt alle 64 Sprites. Overworld-Spalten: `pair_meta(e)` (`me[]`/`mo[]` aus `cell_meta[]`, je Attributpaar), `col_tiles(mm)` (Kacheln nach `colbuf`), `col_attr()` (`attrbuf`), dazu `ppu_flush` in `crt0.s` jetzt mit entrollten Schleifen (60 `lda/sta`-Paare statt Schleife, das spart auch VBlank-Zeit beim Scrollen).
- **Leere Szenenzelle:** `META_BLANK` = 44 (Kacheln und Palette 0) statt der Sondermarke 255; so braucht die Asm-Schleife keinen Vergleich. `bgart.py` erzeugt den Eintrag und die Makros `META_T` (Definition in `main.c` mit `META_DEF`, sonst `extern`).
- **Tor-Zustand:** `cell_meta[]` ist jetzt RAM (44 Byte, `DATA`); `gate_meta()` setzt vor jedem Neuaufbau (`redraw_overworld`) die Einträge 16..25 aus `dungeons_cleared` (offen 42, verschlossen 16), `meta_of()` entfällt.
- **Arena:** `arena_row(r)` baut eine Nametable-Zeile in `rowbuf[32]` (`memset` plus nur die Sonderspalten: Wandränder, Säulen, Plattformen, Dungeon-4-Lava, Dungeon-8-Decke) und `ppu_copy` schreibt sie; `arena_tile()` entfällt. Das Bild ist Byte für Byte dasselbe wie vorher (Nametable, Attribute, Paletten und OAM aller Bildschirme vor und nach der Änderung per Skript verglichen).
- **Menü:** `put_big()` ist tabellengesteuert (`big_escaping`, `big_from_hell`, `big_you_escaped`: Kachel-IDs der Logo-Buchstaben als Konstanten aus `ui.h`), `put_text()` und `glyph()` benutzen statische Hilfsvariablen und den Buchstaben-Schnellpfad (cc65 ist ohne Stack-Lokale viel schneller).
- **Regel für neue Bildschirme:** nur die Routinen oben oder Konstantendaten für große Flächen verwenden; kein C-`for` über 1024 `PPU_DATA`-Schreibzugriffe. Messen mit `tests/redraw.lua` (Obergrenze `MAX` = 3).

## Spielstruktur

- Frame-Loop mit NMI. Zustände (`game_state`): 1 Startmenü, 2 Overworld, 3 Dungeon (inkl. Sieg-Bildschirm), 4 Endbild; Titelgrafik und Intro folgen in v0.9. Boot: `main()` ruft `menu_enter()`, erst die Menüwahl (`start_game()`) lädt/initialisiert den Spielstand und baut die Overworld.
- Overworld: horizontales Scrolling, 3 bis 4 Bildschirme. Dungeon: ein Bildschirm, kein Scrolling.
- Boss-Logik als Datentabelle pro Dämon (HP, Phasen-Grenzen in %, Bewegungsmuster) plus kleine Verhaltensfunktionen.

## Speicherstand (PRG-RAM $6000)

Ein Slot im Batterie-RAM (MMC3 PRG-RAM, in `crt0.s` per `$A001` = `$C0` an **und schreibgeschützt**; `save_game()` und `save_clear()` setzen `$80` nur für die Schreibzeit, siehe „Fehlersuche v1.0“). Code: `save_game()` / `load_game()` in `main.c`.

| Adresse | Inhalt |
|---|---|
| `$6000` | Magic `'E'` (`$45`) |
| `$6001` | Magic `'H'` (`$48`) |
| `$6002` | Version (1) |
| `$6003` | `dungeons_cleared` niedriges Byte (Dungeon 1–8) |
| `$6004` | `dungeons_cleared` hohes Byte (Bits 0–1 = Dungeon 9–10; beim Laden `& $3FF`) und **Bit 7 = Ende gesehen** (v0.8, `ending_seen`); Bits 2–6 frei |
| `$6005` | `abilities` (Bit 0 Dash, 1 Doppelsprung, 2 Feuerball, 3 Schild, 4 Schwertwelle) |
| `$6006` | Prüfsumme = (Summe der Bytes `$6000..$6005`) mod 256 |

- **Laden:** einmal beim Start in `main()`, vor dem Zeichnen der Overworld: gültig = Magic, Version und Prüfsumme stimmen. Dann werden `dungeons_cleared` und `abilities` übernommen, sonst bleibt alles 0 („New Game"). Leerer oder zufälliger RAM ist praktisch immer ungültig, weil die Summe zufällig stimmen müsste. Gültigkeit prüft `save_valid()` (`main.c`, auch vom Menü benutzt: CONTINUE und DELETE SAVE erscheinen nur bei gültigem Stand). Geladen wird nur nach **CONTINUE** (`start_game(1)`), nie nach NEW GAME oder im Cheat-Modus. **DELETE SAVE** ruft `save_clear()` (alle 7 Bytes `$6000..$6006` auf 0). **NEW GAME** lässt einen vorhandenen Stand unberührt (er wird erst vom nächsten `save_game()` überschrieben).
- **Speichern:** `save_game()` nach jedem Sieg (`win()`), Prüfsumme als letztes Byte: ein Schreiben, das vom Strom getrennt wird, ergibt einen ungültigen Stand (alles weg statt halb). Ein Slot, kein Backup. **Formatentscheidung v0.8:** das End-Flag nutzt das freie Bit 7 von `$6004`, die Version bleibt **1**. Alte Stände ohne Bit laden unverändert (Flag = 0, Prüfsumme gilt weiter, weil das Byte mit in der Summe steht), ein neuer Stand mit Flag lässt sich auch von altem Code laden (`& $3FF` blendet das Bit aus). Im Cheat-Modus kehrt `save_game()` sofort zurück: der Stand wird nie geschrieben. Bei neuer Version: Versionsbyte hochzählen, alte Stände gelten dann als ungültig (oder Migration einbauen).
- **Tests:** Lua-Schreibzugriffe auf `$6000..` über `emu.memType.nesMemory` laufen gegen den Schreibschutz und bleiben wirkungslos; Tests, die einen Stand vorgeben, schreiben mit `emu.write(a - $6000, v, emu.memType.nesSaveRam)` (`menu`, `redraw`, `ending`, `progress`). Mesen schreibt `tools/mesen/Saves/EscapingFromHell.sav` beim Beenden und lädt es beim nächsten Start. `make test` löscht die Datei vor jedem Skript; `tests/progress.lua` schreibt/verfälscht `$6000..$6006` selbst und nutzt `emu.reset()` (setzt die Konsole zurück, PRG-RAM bleibt).

## Git "dubious ownership" (gelöst)

Der Projektordner gehört UID 1000, Agenten laufen als root. Der Nutzer hat `safe.directory` für diesen Ordner global eingetragen. Falls die Meldung trotzdem auftaucht: `! git config --global --add safe.directory /root/SoftwareApplications/EscapingFromHell` vom Nutzer ausführen lassen. Agenten ändern die globale Config nicht selbst.

## Push zu GitHub

Remote `origin` ist `https://github.com/Rluffy/EscapingFromHell.git` (privat). Für root gibt es keinen SSH-Key, daher HTTPS mit `gh` als Credential-Helper, pro Befehl: `git -c credential.helper= -c credential.helper='!gh auth git-credential' push --follow-tags`. Globale Git-Config wird nicht geändert.

## Selbst spielen (FCEUX unter Ubuntu)

Die Qt-Version von FCEUX flackert unter Wayland. Abhilfe: `QT_QPA_PLATFORM=xcb fceux <rom>` oder in *Options → Video Config* den Treiber SDL statt OpenGL wählen. Die ROM selbst ist in FCEUX 2.6.5 und Mesen2 frame-stabil geprüft.
