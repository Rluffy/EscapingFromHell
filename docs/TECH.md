# TECH – Escaping From Hell

Festgelegt mit dem Nutzer. Entscheidungen, die ein Agent selbst trifft, hier eintragen (Abschnitt „Entscheidungslog").

## Ziel-Hardware

- Echtes NES-Modul, **NTSC (60 Hz)**.
- **MMC3 (Mapper 4)** mit Batterie-RAM. Startwert: 128 KB PRG-ROM, 128 KB CHR-ROM, 8 KB PRG-RAM. Größen anpassen, wenn nötig (hier eintragen).
- Pro Boss und Phase eigene CHR-Bänke (Bank-Wechsel für Phasen und Overworld-Animation).

## Toolchain

- **cc65 2.19**: C für Logik, `ca65`-Assembler für Zeitkritisches (NMI, Scrolling, Sprite-DMA). Keine Fremd-Bibliothek (kein neslib): eigene Mini-Runtime in `src/crt0.s`, C-Laufzeit aus `none.lib`.
- Build: `make` baut `build/EscapingFromHell.nes`. `make clean`, `make test`.
- Python 3 mit Pillow für Skripte in `tools/`.
- Emulator/Tests: **Mesen2 2.1.1 Linux x64** in `tools/mesen/` (nicht im Git). Download: GitHub-Release `SourMesen/Mesen2`, Datei `Mesen_2.1.1_Linux_x64.zip`.
- Ausweichlösung, falls Mesen headless nicht läuft: `fceux` + `xvfb` (`xvfb-run`).
- Installationen (erlaubt): `apt install cc65 gh xvfb python3-pil`.

## Build-Layout

- `Makefile`: `src/*.c` → `cc65 -t none -O --cpu 6502` → `build/*.s` → `ca65`; `src/*.s` → `ca65`; Link mit `ld65 -C cfg/mmc3.cfg ... none.lib`. Ausgabe `build/EscapingFromHell.nes` (262160 Byte = 16 + 128 KB PRG + 128 KB CHR), dazu `.map` und `.lbl` in `build/`.
- `src/crt0.s`: iNES-Header (Mapper 4, Batterie, 8 PRG-Einheiten à 16 KB, 16 CHR-Einheiten à 8 KB, 1 PRG-RAM-Einheit à 8 KB, NTSC), Reset (PPU-Warmup, MMC3-Init, RAM löschen, C-Stack, `copydata`/`zerobss`, `main`), NMI (OAM-DMA von `$0200`, bei `col_pending` `ppu_flush`, dann `$2000` = `ppu_ctrl` und Scroll X = `scroll_x`, `frame_count` erhöhen), IRQ-Stub (`rti`), Vektoren, `wait_vblank()`.
- `src/debug.s`: Testvariablen (Segment `DEBUG`). `src/chr.s`: CHR-Daten (`.incbin build/tiles.chr` = Pattern-Table 0 / Hintergrund, `build/player.chr` = Pattern-Table 1 / Sprites, je auf 4 KB aufgefüllt). `src/map.s`: Overworld-Karte (`.incbin build/overworld.bin`, Symbol `_overworld_map`). `src/main.c`, `src/nes.h`: C-Seite (Zustandsmaschine, Overworld, PPU-Register-Makros, Prototypen). `src/dungeon.c`: Dungeon-Arena (siehe Abschnitt „Dungeon (v0.3)"). `src/menu.c`: Startmenü und Endbild (siehe „Startmenü und Ende (v0.8)"). `src/boss.h`: Boss-Rahmen-Strukturen und Prototypen, geteilt zwischen `dungeon.c` (fest) und den Boss-Dateien (gebankt). `src/imp.c`: Imp (Code + Phasendaten in PRG-Bank 0). `src/ghost.c`: Geist (Bank 1). `src/hound.c`: Knochenhund (Bank 2). `src/snake.c`: Lavaschlange (Bank 3). `src/winged.c`: Geflügelter Dämon (Bank 4). `src/mirror.c`: Spiegeldämon (Bank 5). `src/toad.c`: Riesenkröte (Bank 6). `src/spider.c`: Spinnenkönigin (Bank 7). `src/oni.c`: Oni-Kriegsherr (Bank 8). `src/lord.c`: Höllenfürst (Bank 9).
- Makefile-Regeln: `assets/sprites/<n>.png` → `build/<n>.chr` (`png2chr.py --pad 4096`); `assets/overworld.txt` → `build/overworld.bin` (`tools/mapconv.py`).
- CHR-Bänke: `crt0.s` setzt beim Reset R0..R5 linear (R0=0, R1=2, R2..R5=4..7), also CHR-Offset `$0000-$1FFF` = PPU `$0000-$1FFF`. Hintergrund `$0000`, Sprites `$1000` (PPUCTRL `$88`).

### Linker-Konfiguration `cfg/mmc3.cfg`

- CPU-Speicher: `$0000-$00FF` Zeropage (cc65 + eigene), `$0100` Stack, `$0200-$02FF` OAM-Puffer, `$0300-$033F` `DEBUG` (Spielzustand, belegt bis `$0336`, `$0337-$033F` frei), `$0340-$05FF` BSS/DATA (704 Byte), `$0600-$07FF` C-Parameterstack (512 Byte, wächst abwärts von `$0800`), `$6000-$7FFF` Segment `SAVE` (Batterie-RAM; der Speicherstand belegt `$6000-$6006`, der C-Code greift direkt per Adresse zu, kein Linker-Symbol).
- PRG-ROM: MMC3 im PRG-Modus 0, Aufteilung siehe „PRG-Banking (v0.4)". Fest: `$C000-$FFFF` = Bänke 14/15 (`STARTUP`, `CODE`, `RODATA`, `DATA`-Ladebild, `VECTORS`). Umschaltbar: `$8000-$9FFF` (R6, Boss-Bank), `$A000-$BFFF` (R7, fest auf Bank 1, ungenutzt). Bänke 0..9 haben eigene Linker-Bereiche `BANK0..BANK9`, Bänke 10..13 den Füllbereich `BANKS` (32 KB).
- CHR: ein Bereich `CHR` mit 128 KB, Segment `CHARS`. Kachel 0 leer, Kachel 1 voll (Farbe 1).
- Reset-Init des MMC3: PRG-Modus 0, Bänke 0/1, vertikale Spiegelung (`$A000` = 0, `1` = horizontal), PRG-RAM an (`$A001` = `$80`), IRQ aus (`$E000`).

## Grafik-Pipeline

- Quelle: PNG in `assets/sprites/` (indiziert, NES-Palette, max. 4 Farben pro Palette).
- `tools/png2chr.py` wandelt PNG → CHR-Daten beim Build. Aufruf: `python3 tools/png2chr.py in.png out.chr [--pad N]` (Breite/Höhe Vielfaches von 8; `--pad 4096` füllt auf 4 KB Pattern-Table mit Nullen, Fehler wenn größer).
- Ausgabe: 2bpp-CHR, Kacheln zeilenweise (links→rechts, oben→unten), je 16 Byte: 8 Byte Plane 0 (niedriges Bit), 8 Byte Plane 1 (hohes Bit), MSB = linkes Pixel.

- **Wechsel:** `bank_set(b)` (`crt0.s`, `__fastcall__`, Bank in A) schreibt R6 und merkt sich `b` in `cur_bank` (Debug `$0326`; Reset setzt 13 = keine; Imp-Dungeon: 0). Nur aus der Hauptschleife aufrufen. `dungeon_enter()` ruft `bank_set(bs->bank)`, die Bank bleibt für den ganzen Kampf (und danach in der Overworld) eingeblendet. Es gibt keinen Wechsel pro Frame.
- **NMI:** ruft nie gebankten Code und fasst `$8000/$8001` nicht an (nur `ppu_flush` im festen Bereich). Wird später per NMI umgeschaltet (z. B. CHR-Bänke), muss der NMI das Select-Register `$8000` danach wieder auf den Wert der Hauptschleife setzen (Race) und `cur_bank` bleibt unberührt, weil nur R6 PRG ist.
- **Regeln für gebankten Code (cc65):** Gebankte Funktionen rufen nur Festbank-Code (Kern, cc65-Laufzeit in `CODE`) oder Code derselben Bank, nie eine andere Bank. Daten, die NMI-Zeit oder andere Bänke lesen, nicht in eine Bank legen. Boss-Tabelle (`bosses[]` in `dungeon.c`), Namen und Max-HP bleiben fest (die Bank-Nummer muss lesbar sein, bevor die Bank da ist). Zustand (Boss-RAM, `fb_*`, `rng`, ...) liegt wie bisher im RAM (`dungeon.c`, `extern` in `boss.h`).
- **Neuer Boss in einer Bank:**
  1. `src/<boss>.c` anlegen mit `#pragma code-name("BANKn")` und `#pragma rodata-name("BANKn")` ganz oben (n = freie Bank 0..9; mehrere kleine Bosse dürfen sich eine Bank teilen), `#include "nes.h"` und `"boss.h"`. Funktion `void <boss>_ai(void)` und `const struct phase <boss>_ph[3]`. Vorlage: `src/imp.c`.
  2. `boss.h`: Prototyp und `extern` ergänzen. `dungeon.c`: Eintrag in `bosses[]` (`{ name, hp, n, w, h, y0, <boss>_ai, <boss>_ph }`), `NBOSS` erhöhen. Bänke 0..9 haben ihre Linker-Bereiche schon; für Bank n > 9 zuerst im Linker-Config einen Bereich/ein Segment aus `BANKS` abspalten (Muster `BANK9`, `BANKS` schrumpft um 8 KB).
  3. Neue Quelldatei wird vom Makefile automatisch gebaut (`src/*.c`). `make` und `build/EscapingFromHell.map` prüfen: Segment `BANKn` ≤ `$2000` Byte, nichts davon in `CODE`/`RODATA`.
  4. Kacheln/Palette wie bisher (Tabelle `struct phase`), Test wie `tests/boss.lua` (`cur_bank` = n prüfen).
- **Debug:** `cur_bank` `$0326` (Test: Overworld 13 und `$8000` leer, Dungeon 1 = 0 und `$8000` enthält Code).

## Overworld (v0.2)

- **Karte:** `assets/overworld.txt` (Text, 64 Spalten x 15 Zeilen Metakacheln à 16x16 px = 1024x240 px, Legende im Dateikopf). `tools/mapconv.py` macht daraus `build/overworld.bin`: spaltenweise, 16 Byte pro Spalte (Zeile 15 = Füllbyte 0), 1024 Byte. Zell-ID: 0..15 = Kachelindex (2 Fels, 3 Lava, 4 Wand, 5 Dach sind fest), 16..25 = Tor von Dungeon 1..10, 32..41 = Tür von Dungeon 1..10. Metakachel = eine 8x8-Kachel 2x2 wiederholt (Platzhalter), Palette je Metakachel.
- **Tempelraster:** Tür von Dungeon n in Spalte 6n-3, Zeile 5 (n ungerade) bzw. 3 (n gerade); Dach darüber, Tor direkt darunter, dann ein Pfadstück zum Hauptweg. Start des Spielers: x=32, y=144. Der Code (Rückkehr aus dem Dungeon) und `mapconv.py` (Assert) nutzen dieselbe Formel.
- **Tore:** offen, wenn n == 1 oder Bit n-2 in `dungeons_cleared` gesetzt ist. Zeichnen und Kollision fragen dieselbe Funktion (`is_open`). Das Tor ist als Zell-ID in der Karte, die Kachel (7 verschlossen / 8 offen) wird beim Spaltenaufbau gewählt. Ändert sich die Maske, zeichnet das Spiel alle sichtbaren Spalten neu (Bild kurz aus), ebenso beim Betreten der Overworld.
- **Scrolling:** vertikale Spiegelung (zwei Nametables nebeneinander = 512 px Ring), `PPUCTRL`-Bit 0 + `PPUSCROLL` X aus `cam_x` (Kamera zentriert auf den Spieler, 0..768). Wechselt `cam_x >> 4`, baut die Hauptschleife die nächste Metakachel-Spalte (rechts: `spalte+16`, links: `spalte`) in `colbuf` (2 Kachelspalten à 30) und `attrbuf` (8 Attribut-Bytes) und setzt `col_pending`. Der NMI kopiert nach dem OAM-DMA beides (Inkrement 32, ca. 1300 Zyklen, passt in VBlank). Attribut-Byte deckt zwei Metakachel-Spalten, wird deshalb immer aus beiden Spalten berechnet. Weiter als eine Spalte Sprung (Teleport) oder Maskenänderung: kompletter Neuaufbau bei ausgeschaltetem Bild (`redraw_overworld`).
- **Spieler:** 16x16 Metasprite (4 Sprites, Kacheln 0..3, Palette 0), 2 px/Frame, 8 Richtungen. Kollisionsbox: 8x6 px an den Füßen (x+4..x+11, y+10..y+15) gegen die Zellen. Eintritt: Fußmitte (x+8, y+12) auf Tür-Zelle eines offenen Dungeons + **A**.
- **Dungeon:** `game_state` 3, Details im nächsten Abschnitt. Rückkehr (Sieg oder Start+Select) setzt den Spieler auf die Tür-Zelle.
- Eingabe: Controller 1, `read_pad()` in `main.c`.
- Paletten: Hintergrund `$0F` schwarz, Pfad braun/orange, Fels/Wand rot, Lava orange, Dach/Tore rot/orange/gelb; Sprite-Palette 0 braun/blau/Haut.

## Boss-Rahmen (v0.3)

- **Tabelle** `bosses[]` in `dungeon.c` (Index = Dungeon-Nr. − 1; 10 Einträge, jeder Dungeon hat einen Boss). Eintrag `struct boss`: `name` (Großbuchstaben aus `font[]`), `hp` (Max-HP), `bank`, `w`/`h`/`y0` (Sprite-Breite 16, 24 oder 32 px, Sprite-Höhe 16, 24 oder 32 px, Start-y; ab `w` >= 32 oder `h` >= 32 (`OWN_DRAW` in `dungeon.c`) zeichnet `draw()` den Boss nicht, die KI schreibt ihre Sprites selbst (Riesenkröte, Oni-Kriegsherr, Höllenfürst); `arena_reset` setzt `en.w`/`en.h`/`en.y` daraus), `ai` (Funktionszeiger, läuft jeden Frame), `ph[3]` je Phase `struct phase`: `tile` (erste von 4 Sprite-Kacheln), `spd`/`wait` (Hüpfen), `rate`/`shots`/`fspd` (Feuerbälle), `pal[3]` (Sprite-Palette 1). Neuer Dämon = Tabelleneintrag + `*_ai()` + Phasendaten in einer Bank (Schritte: „PRG-Banking (v0.4)") + Kacheln, `NBOSS` erhöhen. `bosses[]` hat jetzt `bank` und `ph` (Zeiger auf die Phasen in der Bank) statt eingebetteter Phasen.
- **Phasen:** beim Reset aus Max-HP berechnet: Phase 2 ab `hp <= max*70/100`, Phase 3 ab `hp <= max*50/100` (Imp, Max-HP 10: 7 und 5; genau 70 % bzw. 50 % zählt schon zur nächsten Phase). Geprüft nach jedem Schwerttreffer.
- **Phasenwechsel-Effekt:** `boss_fx` = 30 Frames: Boss eingefroren, harmlos und nicht treffbar, alle Feuerbälle weg, Hintergrundfarbe blinkt weiß (4 Frames an/aus), neue Kacheln und Palette gelten sofort. Palette und Namenstext werden am Frame-Anfang (`pal_sync()`, `text()`) direkt in den PPU geschrieben, solange noch VBlank ist (danach `PPU_ADDR` = 0, Arena scrollt nie); deshalb muss diese Arbeit kurz bleiben (Textlöschen ohne Buchstabensuche).
- **Intro:** `dungeon_enter` zeichnet den Namen zentriert in Kachelzeile 10 (Bild aus), `intro` = 75 Frames (1,25 s): Spieler, Boss, Feuerbälle stehen, nur Zeichnen läuft. Danach Text löschen, Kampf. Nach dem Neustart bei 0 Herzen kein Intro.
- **Gegner-HP-Balken** (`bar_sync()` in `dungeon.c`, generisch): 10 Hintergrundkacheln in Nametable-Zeile 2, Spalten 20..29 (`$2054..$205D`), Kacheln 40 voll / 41 halb / 42 leer. Halbschritte = `ceil(hp * 20 / hp_max)` (`hp_max` = Boss-Tabelle), Kachel i voll ab Schritt 2i+2, halb bei 2i+1. Neuzeichnen nur, wenn `en.hp` != `bar_hp` (zuletzt gezeichnet, 255 = erzwingen). Beim Betreten bei ausgeschaltetem Bild gezeichnet (also schon im Intro), danach über denselben Puffer wie Texte (`tb[]`, 12 Byte): `bar_sync()` am Anfang von `draw()` füllt ihn, `text_flush()` schreibt ihn am nächsten Frame-Anfang im VBlank. Ist `tb[]` belegt (Text) oder steht ein Paletten-Update an (`pal_ph != boss_phase`), wartet der Balken einen Frame: Balken und Phasenpalette zusammen in einem VBlank passten nicht (die Palette kam nicht an, im Test aufgefallen). Dank Vergleich mit `en.hp` zeichnet sich der Balken auch nach `emu.write` auf HP und nach dem Neustart bei 0 Herzen neu. Herzen sind Sprites in derselben Zeile, der Balken liegt rechts davon (Hintergrund, zählt nicht zu den 8 Sprites pro Zeile).
- **Besiegt:** `en.hp` 0 → `boss_dead` = 1, Boss und Feuerbälle verschwinden, Arena bleibt, danach läuft der Sieg-Bildschirm (nächster Abschnitt).
- **Imp-KI (`imp_ai`, `src/imp.c`, Bank 0):** nur Boden. Steht `wait` Frames, hüpft dann (`vy` −4, Schwerkraft wie beim Spieler, ca. 30 px hoch, 24 Frames Flug) mit `spd` px/Frame in Richtung Spieler, in 1 von 4 Hüpfern weg. Unabhängig davon alle `rate` Frames `shots` Feuerbälle Richtung Spieler (Start nach 70 Frames). Phase 1 / 2 / 3: Hüpfpause 120 / 80 / 56, Tempo 1 / 1 / 2, Feuerball alle 300 / 200 / 240 Frames (`rate` ist deshalb 16 Bit, ebenso `fb_t`), Feuerball-Tempo überall 1, Phase 3 = Dreifach-Fächer (vertikal −1/0/+1 mit halber Rate, also flach: der untere Schuss trifft nach ca. 8 Frames den Boden, der mittlere läuft am Boden entlang und ist überspringbar, der obere steigt 0,5 px/Frame und fliegt ab ca. 20 px Abstand über den stehenden Spieler; ein Zweifach-Fächer war nicht nötig). Einzelschuss zielt nur nach oben (−1), wenn der Spieler höher steht.
- **Feuerbälle:** 3 Slots (`fb_x`/`fb_y` Debug, `fb_vx`/`fb_vy` intern), 8x8-Sprite (Kachel 28, Palette 2, OAM 52..63), verschwinden an Wänden, Boden und Oberkante. Treffer = −1 Herz (gleiche Routine `hurt()` wie Kontakt: Unverwundbarkeit und Rückstoß). Ein Spucken ohne freien Slot lässt Schüsse aus.
- **Hohe Bosse und `boss_hide`:** Ist `en.h` > 16, zeichnet `draw()` eine dritte Sprite-Reihe (OAM `$40..$47`, Kacheln `tile`+4/+5, Palette 1, `O_ENEMY2`). `boss_hide` (Debug `$0327`, vom Boss-KI-Code jeden Frame gesetzt, `arena_reset` löscht es): Bit 0 → `combat()` ignoriert Schwerttreffer und Kontakt, Bit 1 → keine Boss-Sprites. ## Spielstruktur

- Frame-Loop mit NMI. Zustände (`game_state`): 1 Startmenü, 2 Overworld, 3 Dungeon (inkl. Sieg-Bildschirm), 4 Endbild; Titelgrafik und Intro folgen in v0.9. Boot: `main()` ruft `menu_enter()`, erst die Menüwahl (`start_game()`) lädt/initialisiert den Spielstand und baut die Overworld.
- Overworld: horizontales Scrolling, 3 bis 4 Bildschirme. Dungeon: ein Bildschirm, kein Scrolling.
- Boss-Logik als Datentabelle pro Dämon (HP, Phasen-Grenzen in %, Bewegungsmuster) plus kleine Verhaltensfunktionen.

## Speicherstand (PRG-RAM $6000)

Ein Slot im Batterie-RAM (MMC3 PRG-RAM, in `crt0.s` per `$A001` = `$80` an). Code: `save_game()` / `load_game()` in `main.c`.

| Adresse | Inhalt |
|---|---|
| `$6000` | Magic `'E'` (`$45`) |
| `$6001` | Magic `'H'` (`$48`) |
| `$6002` | Version (1) |
| `$6003` | `dungeons_cleared` niedriges Byte (Dungeon 1–8) |
| `$6004` | `dungeons_cleared` hohes Byte (Bits 0–1 = Dungeon 9–10; beim Laden `& $3FF`) und **Bit 7 = Ende gesehen** (v0.8, `ending_seen`); Bits 2–6 frei |
| `$6005` | `abilities` (Bit 0 Dash, 1 Doppelsprung, 2 Feuerball, 3 Schild, 4 Schwertwelle) |
| `$6006` | Prüfsumme = (Summe der Bytes `$6000..$6005`) mod 256 |

- **Laden:** einmal beim Start in `main()`, vor dem Zeichnen der Overworld: gültig = Magic, Version und Prüfsumme stimmen. Dann werden `dungeons_cleared` und `abilities` übernommen, sonst bleibt alles 0 („New Game"). Leerer oder zufälliger RAM ist praktisch immer ungültig, weil die Summe zufällig stimmen müsste. Geladen wird nur nach **NORMAL** im Startmenü (`start_game()` in `main.c`), im Cheat-Modus nie. v0.9 ergänzt Continue / Delete.
- **Speichern:** `save_game()` nach jedem Sieg (`win()`), Prüfsumme als letztes Byte: ein Schreiben, das vom Strom getrennt wird, ergibt einen ungültigen Stand (alles weg statt halb). Ein Slot, kein Backup. **Formatentscheidung v0.8:** das End-Flag nutzt das freie Bit 7 von `$6004`, die Version bleibt **1**. Alte Stände ohne Bit laden unverändert (Flag = 0, Prüfsumme gilt weiter, weil das Byte mit in der Summe steht), ein neuer Stand mit Flag lässt sich auch von altem Code laden (`& $3FF` blendet das Bit aus). Im Cheat-Modus kehrt `save_game()` sofort zurück: der Stand wird nie geschrieben. Bei neuer Version: Versionsbyte hochzählen, alte Stände gelten dann als ungültig (oder Migration einbauen).
- **Tests:** Mesen schreibt `tools/mesen/Saves/EscapingFromHell.sav` beim Beenden und lädt es beim nächsten Start. `make test` löscht die Datei vor jedem Skript; `tests/progress.lua` schreibt/verfälscht `$6000..$6006` selbst und nutzt `emu.reset()` (setzt die Konsole zurück, PRG-RAM bleibt).

## Git "dubious ownership" (gelöst)

Der Projektordner gehört UID 1000, Agenten laufen als root. Der Nutzer hat `safe.directory` für diesen Ordner global eingetragen. Falls die Meldung trotzdem auftaucht: `! git config --global --add safe.directory /root/SoftwareApplications/EscapingFromHell` vom Nutzer ausführen lassen. Agenten ändern die globale Config nicht selbst.

## Push zu GitHub

Remote `origin` ist `https://github.com/Rluffy/EscapingFromHell.git` (privat). Für root gibt es keinen SSH-Key, daher HTTPS mit `gh` als Credential-Helper, pro Befehl: `git -c credential.helper= -c credential.helper='!gh auth git-credential' push --follow-tags`. Globale Git-Config wird nicht geändert.

## Selbst spielen (FCEUX unter Ubuntu)

Die Qt-Version von FCEUX flackert unter Wayland. Abhilfe: `QT_QPA_PLATFORM=xcb fceux <rom>` oder in *Options → Video Config* den Treiber SDL statt OpenGL wählen. Die ROM selbst ist in FCEUX 2.6.5 und Mesen2 frame-stabil geprüft.
